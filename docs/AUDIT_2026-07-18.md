# Scaffold-Engine Whole-Repo Improvement Audit — 2026-07-18

Phase 1 (read-only): 15 subsystem finders x 4 dimensions, 2 adversarial skeptics/finding, synthesis.
Agents: 126 | Raw findings: 55 | Confirmed: 40 | Contested: 9

## Executive summary

The scaffold-engine codebase is mature and genuinely well-hardened: this whole-repo audit surfaced zero critical data-loss, corruption, or auth-bypass defects, and the two-skeptic gauntlet rejected most speculative claims (the confirmed set is dominated by localized quality/reliability polish). The real leverage sits in a small number of latent config/UX foot-guns that silently degrade behavior on the happy path: reranking silently turns OFF whenever candidate count exceeds 20 (the config comment literally invites operators into the trap), the web run-stream SSE feed reconnect-storms forever after every normal completion, and hosted-cloud LLM calls get none of the retry/backoff the Ollama path enjoys. Beyond those three, the highest ROI is a dense cluster of one-line quick wins (over-redacted /config, lexical /logs ordering, dead constants/fields, a 3x-wrong SSE stall counter) that are cheap to land together. Cross-cutting patterns — SSRF-guard drift across fetch paths, sibling-function defensive-guard divergence, and several half-wired API fields — suggest the codebase would benefit from consolidating a few shared primitives rather than any large structural rework.

## Top 10 highest-leverage fixes

1. Fix rerank candidate-cap mismatch (max_candidates>20 silently disables reranking)
2. Give the web run-stream SSE feed a terminal close frame (stop the post-completion reconnect storm) + heartbeats
3. Add provider-agnostic retry/backoff (incl. Anthropic 529) to OpenAI/Anthropic role-routed calls
4. Gate /config secret-redaction on value type so 10 non-secret int fields stop being redacted
5. Order GET /logs by execution_order instead of lexical node_key
6. Route research topic-mode + verify-recheck fetches through the guarded §17.93 SSRF/byte-cap helper
7. Anchor the assist rm -rf destructive-command regex to a real -r/-f flag
8. Make node_editor edit the field execution actually consumes (prompt_template), not the discarded optimized_prompt
9. Fix gt_list pagination total to honor the domain + supersede filters
10. Bound recent_jobs_costs to the requested window (join-then-aggregate) instead of scanning all llm_call_logs

## Cross-cutting themes

- SSRF/fetch-guard drift: the §17.93 hardened fetch helper (byte cap + _is_public_host pre/post-redirect) is bypassed by research topic-mode fetch and verify-recheck. Root fix is one shared guarded fetch primitive that every URL source is forced through, closing the exact 'new caller silently bypasses the guard' drift the guard was built to prevent.
- Config/cap inconsistency foot-guns: independently-chosen bounds interact destructively or advertise capability they don't deliver — rerank 512-vs-20, /config over-redaction of ints, and unbounded list endpoints. Reconcile paired caps and make bounds self-consistent.
- Sibling-function defensive-guard divergence: near-identical code paths diverge because a shared hardening pattern was adopted in one and not its twin — case-sensitive vs case-insensitive CodeGen/Shell checks, assist_done missing the JSON-decode guards its siblings have, model_ab missing the research path's rowcount audit, extract_ground_truths missing distill_entries' dict-filter. Extract the guard into a shared helper.
- SSE lifecycle correctness: terminal-close semantics (reconnect storm), missing heartbeats (proxy idle-timeout drops), and a 3x-undercounting stall timer all cluster in the streaming layer and are cheap to fix together.
- Half-wired / dead API surface: handoff_policy, JobSummary.parent_job_id/component_index, the assist divergence flag, and StackOverflow disputed-claim ingest are all accepted/stored/advertised but never consumed. Either wire them or drop them so the contract matches reality.
- Holding a pooled DB connection / row lock across multi-minute LLM calls: compile synthesis (confirmed) and DAG generation (contested/deliberate) both pin connections across model round-trips, violating the documented no-session-across-LLM policy the §17.598 artifact isolation already established.
- Batching opportunities: several read/write loops do N sequential round-trips where one batched statement suffices (Pass-1 exact-hash dedup, provenance writes). Low individual impact, correctness-neutral.

## Full ledger

### #1 — max_candidates > 20 silently DISABLES reranking (512-vs-20 cap mismatch trips the partial-result guard)
- **dimension**: reliability | **severity**: high | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: app/modules/rag_pipeline.py:634-665; app/rerankers.py:15,197,210-228; config.py:186; schemas.py:547
- **problem**: settings.rerank_max_candidates and per-request max_candidates both accept 1..512, but rerank_cross_encoder hard-caps input at _MAX_PAIRS=20. When _rerank asks to rank >20 candidates the CrossEncoder scores only 20 and returns 20 items; the §17.260 contract guard `len(rr.items) < len(docs)` then treats a healthy full batch as a corrupt partial result, discards the real cross-encoder scores, sets skipped_rerank=True, and rebuilds every result on the RRF scale — reranking is silently off for the whole query while still paying the CrossEncoder cost. The config comment explicitly invites operators to raise RERANK_MAX_CANDIDATES for a 'deeper rerank', which is the exact opposite of what happens.
- **fix**: Reconcile the caps: clamp max_cand to _MAX_PAIRS in _rerank (docs = results[:min(max_cand,_MAX_PAIRS)]), OR parameterize/raise max_pairs to honor the requested count, OR treat len(items)==min(len(docs),_MAX_PAIRS) as a valid full result rather than partial-failure. Lower the config/schema le= bound to match whichever cap is authoritative.

### #2 — Web run-stream SSE feed reconnect-storms after every completion and sends no heartbeats
- **dimension**: reliability | **severity**: high | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: app/web/routes.py:1056-1080 (run_stream); app/templates/web/_run_section_streaming.html:8-12; app/static/vendor/htmx-ext-sse-2.2.2.js:209-244; sdk aiter_execute_all (async_client.py:317)
- **problem**: run_stream renders even terminal events as `event: message` then returns; with no `sse-close` attribute the EventSource auto-reconnects on the clean stream close, re-POSTs /execute/all, hits the completed-job guard ('Job already completed; cannot re-execute'), renders that as another terminal message, and loops indefinitely — appending unbounded <li> error banners and re-running DB queries. The §17.455 poll is off in completed state so the section is never cleaned up short of a manual refresh. Separately, aiter_execute_all defaults include_heartbeats=False so the orchestrator's deliberate `: keepalive` frames are stripped, leaving the stream idle during long nodes and vulnerable to proxy idle-timeout teardown (which then feeds the reconnect loop). The template comment 'connection closes automatically when the pipeline completes' is simply wrong.
- **fix**: Emit a distinct `event: close\ndata: done` frame after breaking on a terminal event (and in the except branch) and add `sse-close="close"` to the <ul> so the extension calls source.close(). Pass include_heartbeats=True to aiter_execute_all and forward heartbeats as `: keep-alive` comment lines. Optionally swap the run-section to a static 'completed — refresh for output' fragment on close.

### #3 — OpenAI/Anthropic role-routed calls get zero retry/backoff — the retry cascade is Ollama-only
- **dimension**: reliability | **severity**: high | **effort**: M | **quick_win**: False | **confidence**: confirmed
- **locations**: app/model_router.py:455-464,491-500,792-815,377-434; app/providers/openai.py:120-122,383-449; app/providers/anthropic.py:200,465-542
- **problem**: The module's headline 'retry cascade (3x same model -> fallback swap)' with full-jitter backoff lives only inside _dispatch_with_retry, which is structurally Ollama-only. Role-routed openai/anthropic generate/chat/tool_call/embed call the provider directly; each provider._request issues a single httpx POST with no retry loop and even discards the fallback kwarg. A single transient OpenAI 429/500/503 or Anthropic 529 overloaded_error hard-fails the whole LLM call. The asymmetry is backwards — hosted APIs throttle MORE than a local Ollama yet have the LEAST resilience — and _format_provider_error has no 529 branch, so the operator gets no hint. Reachability is config-gated (all roles default to provider=ollama), so this only bites operators who bind a role to a cloud provider.
- **fix**: Factor the retry/backoff loop out of _dispatch_with_retry into a provider-agnostic wrapper (it already operates on ModelResponse.success + _classify_failure string parsing). Wrap provider.generate/chat_completion/tool_call for the role path in it, add 529 to _RETRYABLE_HTTP_CODES, and add a 529 'overloaded' hint to _format_provider_error.

### #4 — /config over-redacts 10 non-secret int fields via bare substring keyword match
- **dimension**: quality | **severity**: medium | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: app/main.py:1080-1107 (rule at 1103), consumed by get_config 1140-1163; app/config.py
- **problem**: _is_secret_field treats any field whose name merely contains 'key'/'secret'/'token'/'password'/'pass' as a secret. Because it is a bare substring test, it redacts 10 non-sensitive int config values (every *_max_tokens field, plus tool_call_coax_min_tokens and fetch_cache_max_keys) to '(set)' and lists them in the `redacted` array. Redacting an int gives zero security benefit and directly defeats the endpoint's documented U.5 purpose (a config dump safe to paste into bug reports) — an operator debugging token-budget or cache-cardinality config cannot see the values.
- **fix**: Gate the name-keyword rule on value type: apply it only when isinstance(value, str), keeping the SecretStr rule unconditional. All 10 false positives are ints so they stop being redacted while the 5 genuine secrets (3 SecretStr + github_token/huggingface_token str) still match. Alternatively match on word-boundary/suffix (endswith('_key','_token','_secret','_password')).

### #5 — GET /logs orders nodes lexically by node_key, mis-ordering and mis-paginating jobs with 10+ nodes
- **dimension**: reliability | **severity**: medium | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: app/routers/status.py:335-346
- **problem**: The paginated node query in get_logs sorts by node_key (a TEXT column holding LLM-assigned ids T1..Tn) instead of the canonical integer execution_order used by every other read path (get_dag, execution_handler, workflow, prompt_inspector, etc.). Lexical order places T10/T11 before T2, so any job with 10+ nodes renders its log out of order; worse, LIMIT/OFFSET slice this non-monotonic order so page boundaries scramble the sequence across pages. Read-only display defect, no execution impact, but it defeats the endpoint's purpose.
- **fix**: Change `ORDER BY node_key` to `ORDER BY execution_order` (optionally `execution_order, node_key` as a stable tiebreaker), matching get_dag and execution_handler.

### #6 — Research topic-mode fetch and verify-recheck bypass the §17.93 SSRF + byte-cap guard
- **dimension**: reliability | **severity**: medium | **effort**: M | **quick_win**: False | **confidence**: confirmed
- **locations**: app/modules/research_agent.py:146-160 (_fetch_and_extract); app/modules/research_verify.py:168-197 (_recheck_one_url); contrast app/modules/research_extractors.py:433-489
- **problem**: Two fetch paths skip the hardened _fetch_url_bounded helper. (1) Topic-mode _fetch_and_extract does raw client.get + resp.text with no response-size cap and follow_redirects=True — an arbitrarily large or adversarial body is buffered fully into orchestrator RAM (up to research_fetch_concurrency=5 concurrent bodies), and a public search-result URL can 3xx-redirect to a private/metadata IP with no post-redirect host check. (2) verify-recheck validates source_url once with _is_public_host but then issues HEAD/GET with follow_redirects=True and never re-validates the final host, so under ?recheck/?compare_hash it becomes a reachability/status/hash oracle for internal hosts. Both are the exact bypass class §17.93 closed elsewhere; source_url/search URLs are attacker-influenceable via ingested pages.
- **fix**: Route both through the shared guarded fetch primitive: enforce a streamed research_max_url_bytes cap and re-validate str(resp.url) with _is_public_host after the redirect chain (as _fetch_url_bounded already does). Ideally make _fetch_url_bounded the single choke point for all URL fetches so future callers can't drift past the guard.

### #7 — Destructive-command safety gate fires on ordinary rm (including the SAFE rm -i)
- **dimension**: quality | **severity**: medium | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: app/modules/assist_guide.py:601
- **problem**: The rm -rf detector regex `\brm\s+(-[a-zA-Z]*\s+)*-?[a-zA-Z]*[rf]` requires neither a leading dash nor the -r/-f flags — it matches any first token after `rm ` merely containing r or f. So `rm config.conf`, `rm myfile`, and even the interactive-safe `rm -i file` are all reported as 'recursive/forced file deletion (rm -rf)'. This is a safety gate: crying wolf on everyday rm trains operators to ignore its warnings, blunting it for the genuine `rm -rf /` case, and violates the module's own 'only an actual command form trips the gate' contract. Advisory-only (does not block), so impact is desensitization.
- **fix**: Anchor to an actual flag token, e.g. `\brm\s+(-\S*\s+)*-\S*[rf]` requiring a dash on the flag. Add unit cases asserting `rm file.conf` and `rm -i file` do NOT trip while `rm -rf`, `rm -fr`, `rm -r` do.

### #8 — gt_list pagination total/total_pages ignore the domain + supersede filters applied to the listing
- **dimension**: reliability | **severity**: medium | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: app/modules/gt_browser.py:110-115 (_count_entries), 136-174 (gt_list); GET /gt/list app/routers/gt.py:39-62
- **problem**: gt_list computes total via _count_entries(col) which runs col.query(filter="") — an unfiltered count of the whole toon_v2 collection — while the actual page applies entry_id!='' plus an optional domain== clause AND (default include_history=False) supersedes_id=='' to hide superseded versions. So total and derived total_pages overstate visible rows whenever any entries are superseded (the default view) or a domain filter is passed, producing phantom trailing pages that return empty entry lists (the OWUI browser renders has_more = page < total_pages).
- **fix**: Make _count_entries accept and apply the same filter expr used for the listing (count(*) query with expr). Keep the unfiltered call for gt_stats' grand total.

### #9 — SSE stall detection undercounts elapsed time 3x with default keepalive_interval
- **dimension**: reliability | **severity**: medium | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: pipelines/scaffold_router.py:2746-2754,2827-2843; keepalive_interval default at 524
- **problem**: In _stream_sse_to_queue read_timeout = max(30, keep) but on each ReadTimeout the idle counter advances by only `keep` and the threshold is max_idle = max(300, 5*keep). With the default keep=10, each ReadTimeout cycle is ~30s of real silence yet only advances idle_seconds by 10, so the 300s stall backstop isn't reached until ~900s of actual silence, and the emitted stream_stalled payload reports idle_seconds=300 when ~900s elapsed. The inline comment claiming each cycle covers exactly `keep` wall-clock seconds is only true when keep>=30. Delayed/misleading diagnostic, not data loss.
- **fix**: Increment by the true per-cycle duration: `idle_seconds += read_timeout` (not `keep`), and correct the comment.

### #10 — recent_jobs_costs aggregates the entire llm_call_logs table on every call (no time bound on inner subquery)
- **dimension**: performance | **severity**: medium | **effort**: S | **quick_win**: True | **confidence**: confirmed
- **locations**: app/modules/observability_rollups.py:214-240 (subquery 225-236), recent_jobs_costs at 353; GET /observability/jobs
- **problem**: The derived table `SELECT job_id, COUNT(*)... FROM llm_call_logs WHERE job_id IS NOT NULL GROUP BY job_id` has no time bound; only the outer jobs set is windowed. Because it is the nullable side of the LEFT JOIN and the window predicate references jobs, Postgres cannot push it down — it fully aggregates the entire, unbounded, never-pruned llm_call_logs table before hash-joining to the small windowed set. A 'last hour' query scans months of history and degrades linearly with total LLM-call volume regardless of window. Sibling readers (llm_rollup, cost_rollup, _NODE_QUALITY_SQL) are correctly bounded.
- **fix**: Rewrite join-then-aggregate: `FROM jobs j LEFT JOIN llm_call_logs c ON c.job_id=j.id WHERE j.created_at >= NOW()-make_interval(...) GROUP BY j.id,...` so the planner filters jobs first and probes via idx_llm_call_logs_job_id.

### #11 — Editing a node's prompt via node_editor is silently discarded on re-execution
- **dimension**: quality | **severity**: medium | **effort**: M | **quick_win**: False | **confidence**: confirmed
- **locations**: app/modules/node_editor.py:31-35,204-238; app/modules/execution_agent.py:328-330,371-373,705,1176,1241,415; app/web/routes.py:861-883
- **problem**: node_editor exposes optimized_prompt as EDITABLE+INVALIDATING: editing it bumps edit_version, cascade-resets node+downstream, and re-opens the job — returning 200 'ok'. But the executor never reads optimized_prompt; _build_prompt builds from prompt_template and re-runs optimize_prompt, overwriting the column. prompt_template (the field execution consumes) is not editable at all. So an operator's prompt fix is discarded: the re-run regenerates the identical prompt and re-optimizes, ignoring the edit, while the UI reports success. The module docstring claims invalidating fields 'change what the node produces' — false for optimized_prompt.
- **fix**: Make prompt_template the editable+invalidating field, OR on re-execution honor a hand-edited optimized_prompt (execute it directly with skip_optimize). At minimum remove optimized_prompt from EDITABLE_FIELDS so operators aren't misled.

### #12 — Compiled-output LLM synthesis runs while holding an open DB session (violates no-session-across-LLM policy)
- **dimension**: performance | **severity**: medium | **effort**: M | **quick_win**: False | **confidence**: confirmed
- **locations**: app/modules/execution_agent.py:846-916,936-965,1589-1651; app/modules/execution_compile.py:119-199,334,419
- **problem**: In all three finalize paths, _compile_output(job_id, db) is awaited inside the still-open finalize session. When compile_synthesis is enabled (per-job override resolvable even though global default is off), it makes a model_router.tool_call plus, on success, grounding-gate faithfulness/CoVe LLM calls (default ON) — holding an asyncpg pool connection across a multi-second-to-minutes model call. This contradicts the execute_next_node docstring policy and the §17.598 artifact-isolation pattern (which already moved the persist path to its own session but left synthesis behind). No correctness impact; pool exhaustion is impractical given pool=30 vs global concurrency 2.
- **fix**: Compute the compiled/synthesized text with no session held (or a dedicated short-lived one), then re-open a fast session solely for the UPDATE jobs SET compiled_output=..., mirroring the §17.598 artifact isolation.

### #13 — Default replan policy runs a verifier LLM call per submit whose only output (assist_steps.divergence) is surfaced nowhere
- **dimension**: feature | **severity**: medium | **effort**: M | **quick_win**: False | **confidence**: confirmed
- **locations**: app/modules/assist_replan.py:332-376,419-432; default policy db/init.sql:396, routers/assist.py:32
- **problem**: context_only is the DEFAULT replan_policy. ### #14 — Node-count truncation can drop the deliverable/terminal node and silently orphan its dependents
- **dimension**: reliability | **severity**: medium | **effort**: M | **quick_win**: False | **confidence**: confirmed
- **locations**: app/modules/dag_generator.py:992-1010 (truncate), 902-904 (leaf re-derivation)
- **problem**: _enforce_node_count truncates a >10-node DAG by keeping the lowest-numbered ids, ignoring topology and is_deliverable; it strips kept nodes' depends_on refs to dropped nodes and only logs a dag_truncated warning. If the terminal synthesis/output node (typically highest-numbered) is the deliverable, it's dropped, and the persist-time fallback silently re-marks the mutilated leaf set as deliverable — so the user's requested artifact is never produced with no error raised. Neither validate_dag nor _validate_graph checks node count or deliverable survival. Gated behind the model exceeding the explicit max-10 prompt cap, so low frequency but silent when hit.
- **fix**: When truncating, preferentially preserve is_deliverable and terminal output/validation nodes (drop from the middle of the topology, not the tail); if truncation would drop any is_deliverable node, surface a hard warning/error instead of silent leaf re-derivation.

### #15 — extract_ground_truths + format_toon_rows crash on LLM field-type drift (skips distill_entries' dict-guard)
- **dimension**: reliability | **severity**: medium | **effort**: S | **quick_win**: False | **confidence**: confirmed
- **locations**: app/modules/gt_extractor.py:664-682 (no isinstance filter), 173-186 (format_toon_rows); contrast distill_entries at 537; POST /gt routers/gt.py:29
- **problem**: extract_ground_truths reads args['entries'] with only a list-type check (no per-element isinstance(dict) filter), unlike distill_entries which filters non-dicts precisely for the documented phase2_distill_shape_drift case (model emits an array of strings). A string element makes format_toon_rows call entry.get(...) on a str -> AttributeError, an unhandled 500 that breaks the function's status-dict contract, and /gt has no try/except. Separately, format_toon_rows does entry.get('tags','').split(',') — tags-as-list drift raises AttributeError on both the extract path AND the phase2 research path.
- **fix**: Have extract_ground_truths delegate distillation to distill_entries (inheriting its dict-filter and eliminating the duplicated inline tool_call), and harden format_toon_rows to coerce tags defensively (accept list or str) so field-type drift degrades instead of raising.

### #16 — StackOverflow min_score gate and disputed-claim ingest are dead (search hard-constrained to accepted:True)
- **dimension**: feature | **severity**: medium | **effort**: S | **quick_win**: False | **confidence**: confirmed
- **locations**: app/utils/forum_ingest.py:134-142,155,217-264; research_modes/forum.py:67-71

### #17 — GET /jobs/{job_id}/artifacts returns full content of every artifact in the list view

### #19 — JobSummary declares parent_job_id/component_index but no endpoint populates them (and two divergent JobSummary classes)
